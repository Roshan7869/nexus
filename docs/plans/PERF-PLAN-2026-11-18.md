# NEXUS Performance Optimization — Execution Plan

**Date:** 2026-11-18 · All baselines measured today on this machine (i5-1135G7 4C/8T, 16 GB, no CUDA,
Windows 11, venv Python 3.13.18, ONNX fastembed, DB at `D:\nexus-data\db\nexus.db`, 5,066 resources).

### Where the 750 ms actually goes (cProfile, 3 warm calls = 2.29 s)

| Consumer | Cost | Note |
|---|---|---|
| `sqlite3.execute` × **96/request** | ~290 ms/req | aggregation + lookups |
| `fetchall` × 39/request | ~96 ms/req | |
| connection **open+close × 19/request** | ~42 ms/req | raw `sqlite3.connect` + PRAGMAs per module |
| v4 `route_task` run inside v5's L1 | ~372 ms/req | full legacy pipeline re-run just for intent |
| `find_matching_skills` (×2) | ~137 ms each | COUNT + GROUP BY per call |
| write path (routing_log + activation log + commits) | ~140 ms/req | 3 write sites per request |
| query embedding (×6/request!) | ~18 ms/req | same query re-embedded at L1, L2, ISO, cluster |

**Conclusion: routing is SQLite-bound and architecture-bound, not model-bound.** The embedder is 3 ms — swapping it for anything faster buys nothing.

## 2. Phases

### P0 — Instrument (≈1 h) — *nothing is optimized until it is measured*

| Step | Work |
|---|---|
| 0.1 | `scripts/perf_probe.py`: run the 10 heterogeneous probe queries + 20 golden-set queries, report p50/p95/cold, emit JSON receipt to `evals/results/perf/`. Baseline committed today's numbers. |
| 0.2 | Wire `latency_ms` into every `routing_log` write (column already exists; `ensure_routing_log_schema` added it). One `time.perf_counter()` pair around `route_for_task`. |
| 0.3 | `EXPLAIN QUERY PLAN` dump of the top-10 hot queries → `docs/plans/perf-queryplans.md`. |

**Gate to exit:** every future phase re-runs `perf_probe` and archives the delta.

### P1 — DB-layer quick wins (≈4 h) — target **p50 ≤ 350 ms**

| Step | Work | Expected |
|---|---|---|
| 1.1 | **One shared read connection** for the route path. Every module currently opens its own `sqlite3.connect` + PRAGMAs (19 opens/request). Route all reads through `server.db.get_connection()` with a thread-local cached handle; writes keep short-lived connections. | −80–150 ms |
| 1.2 | **Cache request-invariant aggregates.** `COUNT(*) routing_log` and the `cluster_sizes` GROUP BY never change within a request and rarely between — memoize 60 s, invalidate on absorb/report. | −50–80 ms |
| 1.3 | **Index the plans that scan.** From 0.3's dump: add only indexes the plans prove missing (candidates: `resources(status, resource_type)`, `cluster_membership(cluster_name)` covering). No speculative indexes. | measured per query |
| 1.4 | **One commit per request.** routing_log + cluster_activation_log + routing_decisions write sites batch into a single transaction at request end. | −60 ms |

### P2 — Restructure L1 (≈4 h) — target **p50 ≤ 250 ms, p95 ≤ 400 ms**

| Step | Work | Expected |
|---|---|---|
| 2.1 | **Slim the L1 intent probe.** v5 currently runs the *entire* v4 `route_task` pipeline (cluster detect, keyword matching, edge graph, logging) just to extract intent. Replace with: `detect_cluster` + `classify_task` + top-3 ISO — no writes, no edge pass. | −150–300 ms |
| 2.2 | **Embed the query once per request.** It is currently embedded ~6× (L1, L2, ISO, cluster decider). Thread one embedding through the request context. | −15 ms + coherence |
| 2.3 | Route query embeddings through the existing TTL cache in `tool_attention_v4` (256 entries / 5 min — already built, bypassed by the route path). Repeated queries become free. | repeat queries ~free |

### P3 — Populate the hybrid vector lane (≈2 h) — *correctness first, speed second*

| Step | Work |
|---|---|
| 3.1 | Backfill `chunk_embeddings` from `ingestion_chunks` bodies (~4,521 chunks ≈ 90 s at 16 ms). It is **0 rows today** — the designed FTS5+vector hybrid (`retrieve_chunks(vec=True)`) has no vector side, which is why a separate full-corpus ISO pass runs instead. |
| 3.2 | Load `sqlite_vec` in the shared connection helper so `vec_chunks` (bit[384]) exists per connection; verify population. |
| 3.3 | With the hybrid live, make the route path's separate ISO full-corpus scan skippable behind a flag — measure before removing. |

**Gate:** golden-set accuracy must *improve or hold* — this phase changes ranking inputs.

### P4 — Cold start + refresh pipeline (≈4 h)

| Step | Work | Target |
|---|---|---|
| 4.1 | Remove import-time side effects from `unified.py`'s import graph (`context_harness/server.py` constructs its engine and registers backends at *import*; make both first-use). | import ≤ 0.8 s; server-to-healthy ≤ 8 s |
| 4.2 | Obsidian publish: **state-file diff** (hash per note, like `wenlan_sync` state) + bounded 4-worker parallel PUTs (test 50 first). | 5,073 notes: 5 min → ~1.5 min first run; **no-op refresh < 10 s** |
| 4.3 | Backfill: hash-guard bodies (skip unchanged) instead of `--force`; batch 16→64. | re-embed only what changed |
| 4.4 | `build_edges`: `argpartition` top-k instead of full `argsort`; skip entirely when resource count is unchanged (incremental edges for new ids only). | reindex no-op < 5 s |
| 4.5 | Wenlan: keep serial and incremental (fragility is proven — two daemon deaths). Candidate for retirement per the standing decision. | — |

### P5 — Verify (≈1 h)

- Re-run `perf_probe` + **golden-set eval (105 cases)** — accuracy regression invalidates any phase that touched ranking (P2.1, P3).
- Archive receipts to `evals/results/perf/`.
- Update `docs/SETUP-2026-11-18.md` performance section.

## 4. Non-goals (things that would *look* like work)

- **No embedder swap for speed** — 3 ms/query; anything faster is invisible behind 430 ms of SQLite.
- **No Redis / no new infra** — in-process caches cover every measured case.
- **No parallelizing Wenlan** — the daemon died twice under modest serial load.
- **No routing-weight tuning** — that is A/B-gated separately (`run_ab_suite`), not a perf task.
- **No fiber-layer expansion** — parallelism is not on the critical path (see the A11 verdict).

## 5. Order and why

```
P0 (measure) → P1 (DB) → P2 (L1) → P3 (vector lane) → P4 (ops) → P5 (verify)
   cheap           biggest      removes the          correctness      batch
   1 h             single win   architectural        + small perf     jobs
                   ~250 ms      double-run
```

P1+P2 alone should take p50 from 750 → ~250 ms. P3 is required for the hybrid design to exist at all.
P4 makes the weekly refresh cheap enough to actually schedule. Every phase is independently verifiable
and independently revertable; none changes ranking semantics except P2.1/P3, which are golden-set-gated.
